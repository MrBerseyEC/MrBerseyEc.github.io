Thinking concurrently means working out which parts of a problem can be dealt with at the same time, and which have to wait for something else to finish first. Done well, more work gets finished in the same time. It also brings problems that a program doing one thing at a time never has.

Concurrent or parallel?

Three programs need to run. Two of them spend some of their time waiting, for the user or for the network, and while they wait they do not need the processor. Compare three ways of running them.

Using a processor Waiting for input or the network Ready, but waiting for a processor

Concurrent processing

Several processes are in progress over the same period. Each is given a slice of processor time in turn, so they appear to run simultaneously even on a single processor. Nothing happens at exactly the same instant.

Parallel processing

Several processors, or cores, each execute different instructions at exactly the same instant. This cannot be done with a single processor. Its aim is to speed up the computation.

What can happen at the same time?

A task can start only when everything it depends on has finished. Tasks that do not depend on each other can be carried out at the same time, if there are enough processors. Choose a problem and change the number of processors.

The trade-off: shared data

A bank account contains £100. Two processes each pay money in at the same moment: one adds £50 and the other adds £20, so the balance should end up as £170. Each process takes three steps, and the processor can switch between them at any point. Step each process in any order you like. Can you make the bank lose money?

Whether the result is right depends on the order in which the steps happen to be interleaved, so the error may appear only once in thousands of runs. That makes concurrent programs much harder to write, test and debug. Locking a record solves this problem, but it makes other processes wait, and two processes that are each waiting for a record the other has locked will wait for ever. That is called deadlock.






  
Benefits and trade-offs

  

    
Benefits
    
      
  • More tasks are completed in a given time (greater throughput)
    • 
      
  • Time the processor would have wasted waiting for input, output or the network is used for another task
    • 
      
  • A program stays responsive: the interface still reacts while a long task carries on in the background
    • 
      
  • Many users can be served over the same period, as on a web server
    • 
      
  • With several processors, work that splits into independent parts finishes much sooner, such as rendering graphics or processing a large data set
    • 
    

    
Trade-offs
    
      
  • Parts that depend on each other still have to run in order, which limits how much time can be saved
    • 
      
  • If many tasks all need a lot of processing, each of them takes longer to complete
    • 
      
  • Switching between tasks and coordinating them is an overhead. A small job can be faster on a single processor
    • 
      
  • Shared data must be protected with locks, which brings a risk of deadlock
    • 
      
  • Programs are harder to design, write, test and debug
    •
