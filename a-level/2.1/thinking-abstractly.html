Abstraction means removing unnecessary detail from a problem so that only the features needed to solve it are left. The result is a simplified representation of reality. Every computer model, map, simulation and data structure is an abstraction of something.

From a city to a map

Drag the slider to strip detail away from this city, one layer at a time, until only a metro map is left. The table shows which questions each version can still answer.

The metro map is the better tool for planning a journey because so much has been left out. It is also wrong about distance, direction and the shape of every line. An abstraction is judged by whether it keeps what matters for its purpose, not by how closely it matches reality.

Why programmers rely on abstraction

Without abstraction, a programmer would have to think about every detail of the computer at once. Each generation of programming language hid more of the machine, so that the programmer could concentrate on the problem instead. Here is the same instruction at three levels.

High-level language


      
  • Reads like the problem being solved
  • No need to know where x and a are stored
  • Runs on any computer that has a translator

    
Assembly language

      
  • One mnemonic for each machine instruction
  • The programmer manages registers and memory
  • Has to be rewritten for a different processor

    
Machine code

      
  • The binary patterns the processor executes
  • Every opcode and address written by hand
  • Slow to write, and the errors are hard to find

  

  
In programming, abstraction separates what a program unit does from how it does it. This makes large programs possible: a team can design and build a solution in layers, each one using the layer below without needing to understand its insides.






  
Data abstraction: a queue

  
A queue is an abstract data type. The programmer who uses it only needs to know its operations: items join at the rear and leave from the front. How the items are stored is hidden. Use the queue first, then reveal what is going on underneath.

Other kinds of abstraction

  

    
Abstraction by generalisation

      
Grouping things by their common characteristics, giving an "is a kind of" relationship. In 1736 Euler was asked whether a walk through Königsberg could cross each of its seven bridges exactly once. He discarded the streets and buildings, drew each piece of land as a node and each bridge as an edge, and so turned the puzzle into a graph problem. Every node has an odd number of edges, so no such walk exists. The same reasoning now solves any problem of the same kind, in any city.

      
    

    
Where else you have met it

      
    
        
  • Classes and inheritance: Dog and Cat are kinds of Animal, so the shared attributes and methods are written once in the superclass.
    • 
        
  • Procedural abstraction: you call drawTriangle("red", 4.5, 2.0) knowing what it does and what arguments it needs, but not how it draws.
    • 
        
  • Data types: you use an integer or a real number without thinking about how its bits are laid out in memory.
    • 
        
  • Models and simulations: a flight simulator or a climate model keeps the variables that affect the outcome and leaves out the rest.
    •

Metro mapStations, lines, the order of stops and where to changeDistances, directions, streets and the true route of the trackDeciding whether it would be quicker to walk

Model of a housing estateWhere each house and road goesEvery house is identical, with no windows, doors or chimneysA buyer wants to know what their own house will look like

The more you simplify, the easier the model is to build and the faster it runs, but the less likely it is to behave like the real thing. Choosing what to leave out is the design decision.
