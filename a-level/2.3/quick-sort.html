A quick sort is a divide and conquer algorithm, and it is a good example of recursion: a procedure that solves a problem by calling itself on smaller versions of the same problem. It picks an item called the pivot, partitions the list so that smaller items are on one side and larger items on the other, and then quick sorts each side in exactly the same way.

Thinking recursively

  1. Base case. A list with fewer than two items is already sorted. Stop. Without a base case the calls would never end.
  2. Break the problem down. Choose a pivot and partition the list into a part that belongs before the pivot and a part that belongs after it.
  3. Recursive calls. Call quick sort on the left part, then call quick sort on the right part. Each is the same problem, on a shorter list.
  4. Nothing to combine. The partition did the real work, so when every call has finished the list is sorted. A merge sort does its work afterwards, when it merges. A quick sort does it beforehand, when it partitions.
  • Every call is one row in the Recursion tree view of the demo. A call's two recursive calls are drawn on the row beneath it, so the tree grows downwards, and the number of rows is how deep the recursion goes.
  • Only one call is running at a time (solid outline). The calls above it, drawn with a dashed outline, are waiting for it to return. Those waiting calls are held on the call stack.
  • The depth of the tree is the height of the stack, so it is the extra memory the sort needs. A balanced tree is about log₂ n deep. A lopsided tree is up to n deep.
  • It sorts in place, using swaps within the list, so it needs no second list. It is not stable: swaps can change the order of equal items.

Three ways to partition

The recursion is the same whichever method is used. Only the partition step is different, and you can pick any of them in the demo. The first two work in place, swapping items within the one list. The third makes new lists.

Lomuto partition

  1. The pivot is the first item.
  2. Keep a boundary i that marks the end of the group of items that are less than or equal to the pivot. At first the group is empty, so i is at the pivot.
  3. Scan the rest of the list with j. Whenever an item is less than or equal to the pivot, move i on by one and swap that item into the group.
  4. Finally swap the pivot with the item at i, so it sits just after the group. It is now in its final position.
  5. Recurse on the items before the pivot and the items after it. The pivot is not included in either, because it is already in place.

One pointer scans the list. Simple, but a sorted list is its worst case, because the pivot is always the smallest item.

Hoare partition

  1. The pivot is the first item.
  2. Put one pointer, i, just after the pivot and another, j, at the right end.
  3. Move i right past items that are less than or equal to the pivot. Move j left past items that are greater than the pivot.
  4. If i is still left of j, both items are on the wrong side, so swap them and carry on.
  5. When the pointers cross, j is on the last item that is less than or equal to the pivot. Swap the pivot with it, so it is in its final position.
  6. Recurse on the items before the pivot and the items after it. The pivot is not included in either.

Two pointers move towards each other, and the pointers swap items that are on the wrong side, so it usually makes fewer swaps. A sorted list is still its worst case.

Not in place (new lists)

  1. The pivot is the first item.
  2. Make two new, empty lists: smaller and larger.
  3. Go through every other item. If it is less than or equal to the pivot, add it to smaller. Otherwise add it to larger.
  4. Call quick sort on smaller and on larger. Each call returns a new sorted list.
  5. Return smaller + [pivot] + larger, joined into one new list. The pivot is left out of both calls because it goes between them.

This is the easiest version to understand and write, but it is not in place. The lists it creates use extra memory, about O(n log n) in total, where the in-place versions need only O(log n) for the call stack.

The pivot choice matters. A pivot near the middle value splits the list evenly. A pivot that is the smallest or largest value splits off just one item, which is what happens to a first-item pivot on a list that is already sorted. Choosing a random item, or the median of the first, middle and last items, avoids this.
