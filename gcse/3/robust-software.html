Robust software can handle the unexpected without crashing, giving the wrong output or revealing sensitive data. A flaw in a program that compromises security (a code vulnerability) can be exploited by an attacker, so developers look for them through code reviews, and keep an audit trail of who changed what in the code, and when.

Code review

A code review is designed to spot poor programming practice, find vulnerabilities and check efficiency before the code is released. This program has 6 problems. Click the lines you think are a problem, then check your review. You can also run an automated review to see what a tool would find.

Two types of code review

Review by another programmerAutomated review
Who does itUsually someone more senior, with more experienceA specialist piece of software
What it findsBad programming practice and vulnerabilities, including ones that depend on understanding what the program is meant to doCommon, well-known problems, such as vulnerabilities in the programming language and obvious bad practice
DrawbackLabour intensive and time consumingProbably won't identify every issue

Often both are used. If issues are found, the original programmer is asked to improve the code, and then it is reviewed again.

Audit trail

While software is being developed, an audit trail tracks who made which changes to the code, and when. It reduces errors and makes people accountable. If a security issue turns up, it can be traced back to the version of the code where it first appeared. Click a version to see what changed.

Audit trail on a live system

The same idea is used once software is running: the system keeps a log of who did what, and when. It can't stop an attack on its own, but it lets you detect unusual activity, investigate what happened, and hold people accountable. Something odd happened to the Year 10 mock grades.
